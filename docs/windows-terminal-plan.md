# Windows Terminal 接入方案

计划日期：2026-11-02。用户已于 2026-11-03 批准继续构建并自行验证；0.2 原生预览版已实现，交付证据见 [Windows 验证](windows-validation.md)。

建议采用独立的 Windows 后台组件：通过 UI Automation 只读取得终端文字与屏幕位置，在终端上方维护不获取焦点的公式覆盖窗口。用户继续使用现有 Windows Terminal 和原版 Codex。

这属于外部呈现增强，不是加载到 Windows Terminal 内部的官方扩展。它不需要终端开放自定义绘制插件接口。下文保留计划制定时的研究证据及验收门槛；当前结果以验证文档为准。

## 1. 使用者需要做什么

目标流程：

1. 安装 Agent Math，并启用公式显示。
2. 照常打开 Windows Terminal，在 PowerShell 中运行 `codex`。
3. 完整公式出现后自动呈现；从系统托盘可以暂停、恢复或退出。

默认无需更换终端、改写启动命令、调整模型提示词、克隆仓库或运行构建命令。登录启动作为可选设置，不在调研阶段修改用户系统配置。

0.2 安装包已封装固定 Node.js、MathJax/NewCM 和 resvg，不依赖开发机 Chrome。安装包约 40 MB；普通使用者无需另外安装这些组件。登录启动由安装界面显式选择，默认关闭。

## 2. 计划制定时的研究证据

环境：本机 Windows Terminal **1.24.12741.0**；Codex 启动显示版本 **0.166.0**。

| 项目 | 实测结果 | 证据边界 |
| --- | --- | --- |
| 取得公式位置 | UIA `TextPattern` 能读取可见文字，返回公式逐行屏幕矩形 | 已验证受控样本及真实 Codex 历史回答 |
| 在原位置呈现 | 原生覆盖窗口能展示离线排版的公式 | 研究程序预先捕获并渲染单个公式，尚非完整自动流水线 |
| 保持源码 | 覆盖前后的 UIA 文档文字与可见文字一致 | 未取得终端内部全部字符属性和光标数据，不能声称完成逐单元格等价测试 |
| 识别助手正文 | 在有界发现的 160 个本地会话候选中，完整正文唯一匹配，公式与助手记录一致 | 复用现有 Codex 语义匹配器；尚需实现自动会话发现与窗口生命周期的持续联动 |
| 键盘操作 | 真实 Codex 可输入临时字符、使用左右方向键并删除；原文字恢复 | 未发送 Enter，没有请求新模型回答 |
| 滚动 | 在真实 Codex 历史中滚离公式后隐藏，返回后恢复 | 通过 UIA 移动视口；鼠标滚轮的独立验收尚未完成 |
| 重绘与选择 | 受控审批界面重绘后隐藏；UIA 选择源码时隐藏 | 审批为模拟样本；尚未运行真实工具审批 |
| 窗口变化 | 受控窗口移动、缩放、最小化和恢复通过；备用屏幕可显示 | 单窗口、单显示器与单 DPI |
| 不抢焦点 | 原终端保持前台；覆盖位置的原生命中测试返回终端 | 实际鼠标拖选仍待确认：自动拖选在有无覆盖层时均未成功 |

前 1000 次 UIA 读取及窗口更新采样，真实 Codex 的 P50 为 **2.21 ms**，P95 为 **3.84 ms**。这不包含排版、首次发现或 100 ms 轮询间隔，不能等同于端到端显示延迟。受控窗口变化期间出现过一次 COM 异常，研究程序隐藏覆盖后恢复。

完整的脱敏结果见 [windows-terminal-uia-results.json](research/windows-terminal-uia-results.json)，复现方式见[研究记录](research/windows-terminal-uia.md)。历史实验截图保留本地，当前版本的受控终端对比截图见[展示说明](showcase.md)。

## 3. 技术边界与路线取舍

```text
原版 Codex → 现有 PTY → Windows Terminal → 原有文字画面
                             │
                             └─ UIA 只读观察 → 正文校验 → 离线排版 → 原生覆盖窗口
```

原始终端链路仍由原程序与终端管理。组件不向该链路注入 Sixel，不代理 PTY，不修改 Codex 程序，不通过键盘钩子接管输入。复制继续取终端里的源码。

| 路线 | 使用者需要改变什么 | 与当前要求的关系 |
| --- | --- | --- |
| UIA 与原生覆盖窗口 | 安装并启用一个后台组件 | 当前优先路线；仍需通过后续工程关口 |
| PTY 包装器与 Sixel | 通常通过包装命令启动 agent，处理显示数据流 | 能保留终端应用，但与原始数据流不变存在冲突，需要另行讨论取舍 |
| Tabby 绘制插件 | 使用 Tabby 运行 agent | 已有验证原型，但需要更换终端 |
| 修改 Windows Terminal 本身 | 使用定制终端版本并跟随上游维护 | 安装和维护成本较高，不作为当前建议 |

Sixel 是终端图片协议，无法单独解决公式定位、后台观察或显示数据流保持原样的问题。当前优先方案使用 Windows 原生窗口绘图，不依赖 Sixel。

首个产品验收范围建议限定为本地 Windows x64、当前已测 Windows Terminal 版本，以及原生 Windows Codex。其他终端、WSL、SSH、提升权限的终端、透明主题和其他 agent 另行验证。

## 4. 正式构建顺序

| 阶段 | 交付内容 | 进入下一阶段的条件 |
| --- | --- | --- |
| W0：确认显示与输入边界 | 改进实际鼠标测试，验证选择、滚轮、菜单、搜索框、标签切换、多个窗口与面板 | 覆盖层不吞键鼠、不遮住终端菜单，不跨窗口或面板串联；不通过时先讨论取舍 |
| W1：连续自动呈现 | 后台宿主、UIA 工作线程、唯一会话校验、按公式发生位置定位、离线排版调度与缓存 | 在真实 Codex 新回答中自动处理完整块公式，不依赖预先捕获文件；不匹配时保留原文 |
| W2：失效处理与交互回归 | 文本及选择事件、窗口事件、版本校验、超时隐藏、DPI 与主题处理 | 重绘、审批、滚动、缩放和终端关闭时及时隐藏旧图；渲染进程或 UIA 失败不阻塞 Codex |
| W3：简洁安装与试用 | 原生宿主与离线排版组件的单个安装包、托盘开关、卸载与更新 | 在没有项目源码及开发工具的环境安装使用；不要求手动配置 Node.js 或 Chrome；关闭后无覆盖残留 |
| W4：社区预览准备 | 兼容列表、安装说明、演示、问题反馈模板与版本标签 | 本机与独立环境验收有记录，说明已知边界；是否实际发布由用户后续决定 |

优先采用原生 Windows 宿主管理 UIA、覆盖窗口与托盘，复用现有离线排版及 Codex 校验逻辑。通过 W0 后再确定生产排版运行时的打包方式，避免开发环境依赖变成用户安装步骤。

UIA 读取应在独立工作线程进行；事件回调只标记失效。原生窗口的显示线程不能被慢查询阻塞。绘制前校验可见内容与区域版本，超时或状态不明时隐藏。终端内菜单、命令面板、搜索框及焦点变化也必须纳入隐藏规则，不能仅依赖终端 HWND 仍在前台。

全消息唯一匹配仍保持保守策略，不能依赖“最新会话文件”。多个会话内容相同、完整消息被裁切、源码正在输出或可用空间不足时保留原文。用户自定义会话目录的发现方式也需要在打包阶段确定。

## 5. 已批准方向

用户已批准：**Windows Terminal 保持原样，增加一个可启停的原生后台显示组件；先通过 W0，再实现连续自动呈现与安装包。**

如果 W0 表明外部覆盖无法可靠保留必要交互，应带着证据重新讨论，不能默认切换为更换终端或代理输出流的实现。
